== Frontend (single-page application)

The frontend is a vanilla JavaScript SPA served from `public/`; it uses ES
modules and CSS with no framework, Node.js, or build step. The backend serves
the shell in `private/assets/index.html`, which loads the stylesheet and the
entry module into `#app`.

Client path constants live in `public/js/routes.js` and mirror the backend's
`RouteEnum`. `main.js` maps those paths to views, while `nav.js` builds the
navigation. Keep the path map, view wiring, and navigation in sync when adding
or renaming a page.

Public profiles are available at `/user?id=<id>`; visitors can view any
profile, while the signed-in user's own profile links to the `/settings`
editor. User names in image metadata and internal moderation tools link to
their public profiles when the user ID is available.

`api.js`, `router.js`, and `session.js` handle HTTP, history navigation, and
session state. The SPA uses same-origin requests and the browser's HttpOnly
session cookie for authentication; `ApiError.status` carries HTTP failures to
views, which map status codes to user-facing messages. Page modules live in
`views/`; shared helpers include `paginatedTable.js`, `moderationQueue.js`,
`imageMetadata.js`, `tagLinks.js`, and `searchForm.js`. `accessLevel.js` exports
`hasAccessLevel()`, and `validation.js` mirrors backend field rules for faster
feedback.

=== Upload and moderation behavior

The upload view sends each selected file sequentially as multipart field
`image[]`. The home view shows accepted-image thumbnails and any pending-review
images visible to the viewer; pending-review tiles use distinct
`tile-unapproved` styling. The image view loads metadata and a protected
sample, with a download link labeled *Download*.
Image and tag moderation queues act on the currently selected item: Approve
and Reject submit that selection, and a success message remains visible rather
than auto-dismissing. Deleting an image asks for confirmation: Enter confirms
and Escape cancels. A successful deletion opens the previous visible neighbor
with history replacement, or the home page when no previous image exists.

=== Quick tags and layout

Image and Tagme queue views can show a right-hand Quick tags sidebar with up to
20 globally most-used tags on the left and up to 10 user-most-used plus 10
user-recent tags on the right. Buttons add or remove tags from the current
image without confirmation, immediately updating its regular tag list and
silently refreshing the three quick-tag lists so "Your recent" reflects the
change without clearing the success message; the `tagme` system tag is
excluded from suggestions. The lists are fetched when enabled, including when
a view opens with the setting already enabled. A toggle
below the main tag list controls the sidebar; it is off by default, stored in
the session, and reset on login. Pending quick-tag actions use `aria-disabled`
rather than native disabling, so the toggle and tag buttons keep focus and
image-view hotkeys remain usable. `GET /api/tags/quick` supplies the lists,
`POST /api/session/quick-tags` changes the setting, and `GET /api/session`
includes `quickTagsEnabled`.

Home, image, and Tagme gallery pages use a wider content area. Image and Tagme
pages add a third column only while Quick tags are enabled; otherwise the main
content uses that space. The Tags management page uses the two-column workspace
shared with audit log and user management, with the tag table on the left and
search, create-tag, and create-category tools on the right.

Client-page deep links work on reload because their `GET` routes return the
same HTML shell. API errors are handled by status code; exception bodies are
normally empty, although development PHP settings may include a stack trace.
