== Image uploads

Authenticated users can select multiple images. The browser uploads each
sequentially in a multipart `POST /upload-image` request using field `image[]`.
The server recognizes PNG, JPEG, AVIF, and WebP by signature and verifies that
each image can be decoded. Dimensions are checked before GD decoding: neither
side may exceed 16,384 pixels and the image may not exceed 20 million pixels.
The Docker PHP/Nginx configuration allows up to 100 MB per file and request;
manual hosts must set compatible PHP and web-server limits.

Upload validation decodes the image to confirm it is readable and capture its
dimensions, but stores the original bytes unchanged. Before storing anything,
the server looks up the SHA-256 checksum of every file. A checksum that already
exists in the image records is rejected with `409` and no file from that request
is stored; the client-supplied name and extension do not affect the match.
Original files are stored flat as `<sha-256>.<extension>`; generated variants
remain content-addressed in sharded directories. A new image starts pending and
is tagged `tagme`; each successful upload is recorded as an `IMAGE_UPLOADED`
audit action. Uploads can also authenticate with an API key for browser code
(including cross-origin clients using the endpoint's CORS preflight) and
server-to-server clients; see `docs/api/index.adoc`.

The SPA uploads files one at a time. A failed file does not stop the remaining
files, and the view keeps a list of every failed file name with its mapped reason in a dedicated error column next to the form, so later progress messages do not hide earlier failures.
The form is only reset after a fully successful batch.

=== Processing and delivery

The asynchronous worker scans the flat original-upload directory, then looks up
each file's checksum in the image records. As a secondary safeguard, multiple
active records for the same checksum are treated as duplicates: the oldest record
is kept and newer active duplicates are deleted before processing; queued records
are left untouched so they can still be restored. Partial records are fully
regenerated, overwriting their content-addressed variants. If every matching
record is already complete, the worker warns and deletes the redundant original
without reprocessing it. Originals with no matching database record are also
warned about and deleted.
Processing creates a public AVIF thumbnail, a private WebP viewing sample, and a
private download. Downloads remain in the source format except PNG, which becomes
pixel-lossless WebP. The worker moves pending images to the accepted collection
or moderation queue according to the uploader's role.

Run `php src/app.php --process-images 100` to process a batch; Docker runs the
same command every second in the background. If another worker holds the lock
file, this worker exits immediately without processing images. Failed originals
remain on disk for retry. The original is never served to users. Thumbnails are
static public files. Accepted-image details and viewing samples are accessible
anonymously; viewing and download files are delivered through internal Nginx
locations with `X-Accel-Redirect`. Downloads require authentication.

`GET /api/images` returns accepted images to anonymous viewers, plus the
signed-in viewer's own pending-review images; `MOD` and higher can see all
pending-review images. Accepted-image details are public; non-accepted details,
samples, and downloads remain restricted by the image access policy.
Authenticated users can access their own pending-review details and their own
or `tagme`-tagged pending-review samples and downloads; `MOD` and higher can
access all image states. Tag input is capped at 2,048 characters and 20 names,
with a maximum of 100 characters per tag.

`GET /api/image/detail?id=...` returns details for accepted images anonymously;
pending-review details require the uploader or a moderator. The sample and
download endpoints are `GET /api/image/sample` and `GET /api/image/download`;
sample access follows the image policy, while downloads always require
authentication. They deliver files through `X-Accel-Redirect`. Moderators use
`GET /api/review/queue`, `POST /api/review/approve`, and
`POST /api/review/reject`. Approval moves a pending-review image to accepted.
Rejection deletes its row and attempts to delete unreferenced files instead of
assigning a rejected status; a content-addressed file is retained while another
image record references it.

Moderators can also move an image to the delete queue with
`POST /api/image/delete`. The image view does this immediately (no confirmation
dialog) and then opens the previous visible neighbor, or the home page when none
exists, replacing the image in history. Queued images keep their row and files
but are excluded from the home page, profile uploads, tagme, neighbor
navigation, and regular detail/sample/download access. `GET /api/delete-queue`
lists them for `MOD` and higher; `POST /api/delete-queue/restore` makes an image
visible again according to its review status, while
`POST /api/delete-queue/delete` permanently deletes the row and unreferenced
files and records an `IMAGE_DELETED` audit entry.
