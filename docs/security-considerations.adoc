== Security considerations

SmolCms is a learning project, not a production-hardened application. Review
these limitations before deploying it:

* Session cookies are `HttpOnly` and `SameSite=Strict`, but `Secure` is off;
  session IDs are not regenerated and session locking is not implemented
  (<<_session_handling>>).
* Protected handlers enforce a minimum `AccessLevel` and refresh the user's
  role from the database on each protected request. User management forbids
  self-updates, changes to users at or above the actor's level, and grants of
  roles at or above that level. The app does not enforce stored `disabled` or
  `banned` states.
* Users at `WIZARD` level or higher can generate an API key from their profile
  via `POST /api/profile/api-key` (201); the plaintext is shown once, only its
  SHA-256 hash is stored, and regeneration replaces the previous key.
  `#[Authenticated(..., apiEnabled: true)]` opts a handler into
  `Authorization: Bearer <key>` authentication; it is off by default, and only
  `POST /upload-image` currently opts in. API-key-authenticated uploads use the usual access
  check and add `via=api` to the `IMAGE_UPLOADED` audit context.
* State-changing requests have no CSRF token. For `POST`, `PUT`, and `DELETE`,
  the pre-controller check rejects cross-origin `Sec-Fetch-Site` values or an
  `Origin` whose host differs from the request host, unless a CORS-enabled
  handler is called with a Bearer key and no session cookie. The upload
  endpoint returns `Access-Control-Allow-Origin: *` without
  `Access-Control-Allow-Credentials`, so cross-origin session authentication is
  not possible. Rate limiting is also absent.
* Image uploads use signature detection, GD decode validation, and limits of
  16,384 pixels per side and 20 million total pixels. The worker re-encodes
  generated variants; these checks are not a substitute for content
  moderation (<<_image_uploads>>).
* JSON responses are encoded, but the API has no HTML-context escaping layer.
  The SPA renders user-controlled values as text; other consumers must escape
  data for their output context.
* The shipped Nginx configuration serves `/public/` as static content, denies
  `/private/`, and marks protected image locations internal. Treat `/src/` as
  deployment guidance: do not expose it as static content through another
  server configuration.
* Every application response sets `Cross-Origin-Resource-Policy: same-site`.
  Accepted-image details and viewing samples are anonymously accessible, while
  downloads require authentication and pending/private image access remains
  restricted by the image access policy.
* The filesystem allowlist is defense in depth; it does not replace OS
  permissions or prevent check-then-use races and native filesystem bypasses.
* Duplicate registration returns `409`, which can reveal whether a login name
  exists. The audit log records tag additions, removals, and deletions, plus
  image uploads and deletions.
* The shell's generated SRI hash pins its `main.js` entry script; imported
  modules are not individually pinned. Docker development enables
  `display_errors`; its `prod` image target disables display errors but is not
  by itself a hardened deployment.

When adding a feature, keep its frontend and server-side authorization and
validation aligned; see <<_precontrolleraction_chain>> and
<<_frontend_single_page_application>>.
