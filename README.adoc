= SmolCms
:toc: macro
:icons: font

SmolCms is a small PHP web application learning project with routing, templating, user registration and authentication, SQLite persistence (default; MySQL schema included), and experimental image uploads.
It requires PHP 8.5 or newer and the `PDO`, `mbstring`, `PDO_SQLite`, and `GD` extensions (see `composer.json` `require`).
The requirement is enforced by `composer.json` at `composer install` time and at runtime via Composer's generated platform check, which `src/app.php` loads through `vendor/autoload.php`.

The project has no `LICENSE` file and no `license` field in `composer.json` (all rights reserved), and contributions are not currently accepted.
Third-party Composer dependencies (currently dev-only via `phpunit/phpunit`) retain their own licenses.

== Installation and setup

Install the Composer dependencies from the repository root:

[source,shell]
----
composer install
----

The application requires these directories:

* `private/db` for the SQLite database
* `private/sql` for migration files
* `private/upload` and `private/upload/img` for image storage
* `private/init` for the driver-specific schema files

`private/db`, `private/sql`, and `private/upload/img` ship via `.gitkeep` placeholder files.
`private/upload` ships implicitly as the parent of `private/upload/img/.gitkeep` and has no `.gitkeep` of its own.
`private/init` ships via its tracked `init.sql` and `init_sqlite.sql` files.
The `FS_APP_LEVEL_WHITELIST` directories (`private/init`, `private/sql`, `private/upload`) must exist before `FileSystemAccessService` construction; `private/db` and `private/upload/img` must exist before database and image operations, respectively.

The CLI and PHP-FPM users need read access to the application files, including `private/init`.
The CLI user needs write access to `private/db` for `--reset-db` and `--migrations`, and to `private/sql` for `--generate-migration`.
The PHP-FPM user needs write access to `private/db` and to `private/upload/img`.
`private/sql` needs only read access for `--migrations` execution, and `private/upload` itself needs only existence/traverse permission.
PHP's upload temporary directory must additionally be readable and covered by `FS_DIRECTORY_WHITELIST` in `config.php`.

Ignored by Git (see `.gitignore`): `/vendor`, `/composer.lock`, `/.phpunit.cache/`, `/private/db/smolcms.sq3`.
`composer.json` is the tracked dependency source.

Initialize or reinitialize the database with the destructive reset command, which drops tables (not the SQLite file itself) and does not run pending migrations:

[source,shell]
----
php src/app.php --reset-db
----

The command prompts for confirmation even when no tables exist.
Add `--noconfirm` before or after the command to suppress the prompt; `--noconfirm` is a global modifier that also suppresses the `--migrations` prompt and does nothing by itself.
The command loads `private/init/init_sqlite.sql` for SQLite (the default) and `private/init/init.sql` for MySQL; other drivers are rejected.

== Running the application

The canonical entry point is `src/app.php`.
The application uses CLI mode for the commands documented in <<_cli_commands>>.
For HTTP requests, use a web server with PHP-FPM or another CGI-compatible PHP runtime.

`private/references/nginx.conf` contains a reference Nginx configuration.
Adapt its document roots and PHP-FPM socket for the target system.
It serves `/public/` as static files, denies `/private/` with 403, and forwards other requests to `src/app.php` via FastCGI.

The `public/` directory contains only static assets; it has no PHP entry point.
Uploaded images are stored under `private/` and are not publicly served.

== Application flow

The high-level flow of a request (or CLI invocation) is:

. `src/app.php` loads `constants.php`, `config.php`, and `vendor/autoload.php`, builds the service graph via `ServiceBuilder::getService(ApplicationCore::class)`, and calls `ApplicationCore::init()`.
. `init()` runs the startup actions in order: restrict directory access (`open_basedir`), register the DB-backed session handler, and resume the session.
. Under the CLI SAPI, `runCli()` executes the documented commands and exits; under a web SAPI, `runCgi()` builds a `Request` from the PHP globals via `RequestFactory`.
. `handleRequest()` matches the URL path against the configured routes, resolves the controller through the service container, extracts path parameters, and runs the pre-controller chain: authorization, request mapping, then validation.
. The controller handler runs and returns a `Response`; a missing route or a falsy result becomes a `404`, and `Throwable`s from the chain or the controller become empty `400`/`500` responses via `ExceptionResponseService`.
. `output()` sends the response: the status code via `http_response_code()` and the body via `echo`; response headers (such as `Location`) are not sent.

== Project constants

Root-level `constants.php` defines only the global `ROOT_DIR` constant (`__DIR__`).
Root-level `config.php` defines four global path constants derived from `ROOT_DIR`: `FS_DIRECTORY_WHITELIST`, `FS_APP_LEVEL_WHITELIST`, `MIGRATION_DIR`, and `IMAGE_STORAGE_DIR`; it currently holds no credentials.

The production entry point `src/app.php` requires, in order, `constants.php` (via `dirname(__DIR__)`), then `config.php`, then `vendor/autoload.php` via `ROOT_DIR`.
`tests/TestUtils/SimpleTestCase.php` requires `constants.php` then `config.php` at file scope; direct and indirect subclasses (including `FunctionalTestCase`) inherit them via that inclusion, not via per-test requires.
Under PHPUnit, `vendor/autoload.php` loads first via the `phpunit.xml` bootstrap, unlike `src/app.php`.

Note that `config.php` is not the sole place for paths: `GenerateMigrationExecutor` duplicates the migration directory as a private constant, and the `PDO` DSN in `CoreServiceConfiguration` builds the `private/db` path directly from `ROOT_DIR`.

== Early startup configuration

To run code during application initialization, define an instantiable class implementing `SmolCms\Service\Core\Startup\StartupAction` with a `runAction(): void` method and append its service identifier (usually `::class`) to the `parameters` list of the `ApplicationStartupHandler` `Service` defined in the `CoreServiceConfiguration::__construct()` `$services` array; use `addService(..., replace: true)` if replacing programmatically.
`ApplicationStartupHandler::__construct()` is `StartupAction ...$actions`, so non-implementors fail at construction.

[source,php]
----
// Inside CoreServiceConfiguration::__construct(), in the $services array.
// The first three actions are the default configuration;
// MyStartupAction and FancyStartupAction are placeholders for your own additions.
new Service(
    identifier: ApplicationStartupHandler::class,
    parameters: [
        RestrictDirectoryAccessStartupAction::class,
        RegisterSessionHandlerStartupAction::class,
        ResumeSessionStartupAction::class,
        MyStartupAction::class,
        FancyStartupAction::class,
    ],
),
----

The `parameters` entries must be resolvable service identifier strings, not instantiated actions.
Actions are autowired per the rules in <<_configuring_services>>; an action with builtin or otherwise unresolvable constructor parameters needs an explicit `Service` definition with raw values, as `RestrictDirectoryAccessStartupAction` has for its `string ...$directoryWhitelist`.
Custom non-class identifiers also need an explicit `Service(class: ...)` definition.

Identifiers are resolved transitively when `$serviceBuilder->getService(ApplicationCore::class)` builds `ApplicationStartupHandler` (not in `new ServiceBuilder`, not in `init()`), via `ServiceBuilder::getService()` including variadic-tail handling, and are executed in listed order when `ApplicationCore::init()` calls `ApplicationStartupHandler::runActions()`.
The normal bootstrap order in `src/app.php` is `getService(ApplicationCore)` → `init()` → `runCli()` → `runCgi()`; only `ApplicationCore` dependencies are built before `init()`, while route controllers and other lazy services are built later.
`init()` has no guard; each call re-runs `runAction()` on the same cached instances.

== Directory Access Restrictions

During `ApplicationCore::init()` (via `ApplicationStartupHandler::runActions()`), the first default startup action `RestrictDirectoryAccessStartupAction::runAction()` calls `ini_set('open_basedir', ...)` with `FS_DIRECTORY_WHITELIST` spread into it by `CoreServiceConfiguration`.
With the default `config.php` on Unix-like systems, file accesses subject to `open_basedir` after that point are limited to the trees `ROOT_DIR/private` and `ROOT_DIR/src` (symlinks resolved; the parent `ROOT_DIR` itself need not be listed).

`src/app.php` requires `constants.php`, `config.php`, and `vendor/autoload.php`, then constructs the service graph (`ApplicationCore`, `PDO`, `FileSystemAccessService`, startup actions, CLI handlers) via `ServiceBuilder::getService()` before `init()`, so this is not process-start protection.
Keep `ROOT_DIR/src` whitelisted because route controllers and other services are autowired and lazy-loaded with Composer PSR-4 `SmolCms\` → `src` after startup (`ApplicationCore::handleRequest()` plus `ServiceBuilder`).
`vendor/` is currently not whitelisted and needs no post-startup include (there are no runtime Composer dependencies); adding one requires a whitelist and host-config update.
No filesystem access to `ROOT_DIR` itself is needed after bootstrap, but every later include, autoload, and native path (database, migrations, init SQL, image storage) must resolve inside the whitelist.

`ini_set()` affects only the current CLI execution or FPM request.
If the host `open_basedir` is unset, it sets the initial restriction; if already set, it can only narrow it, never widen it, and returns `false` on failure.
The current action ignores that return value.
The host `php.ini` or pool configuration must therefore be unset or a superset of all required paths, including the upload temporary directory.

`open_basedir` neither creates directories nor grants OS permissions.
`private/init`, `private/sql`, and `private/upload` must resolve at `FileSystemAccessService` construction; `private/db` and `private/upload/img` are required by database and image operations.
The default `FS_DIRECTORY_WHITELIST` does not cover PHP's `upload_tmp_dir` (default system tmp); image uploads fail unless the temporary directory is relocated inside the whitelist or the whitelist is extended.

The action joins the whitelist with `implode(':')`, not `PATH_SEPARATOR`; the code assumes a Unix-like runtime.

== Configuring services

The application passes a `CoreServiceConfiguration` and a `ServiceRegistry` to `ServiceBuilder` (see `src/app.php`).
`ServiceBuilder` pre-registers itself, the registry, and the configuration in the registry.
The core configuration creates its initial `Service` definitions in its constructor.
Additional definitions can be added with `CoreServiceConfiguration::addService()`; duplicate identifiers throw `ServiceConflictException` unless the `$replace = true` flag is passed.
This is distinct from `ServiceRegistry::addService()`, which has no replacement flag and always throws on a duplicate key.

A service definition has an identifier (`string`), an optional class (`?string`), and constructor parameters (`array`).
The identifier is the lookup and cache key in both the configuration and the registry.
If `class` is omitted, it defaults to the identifier, so omission succeeds only when `class_exists(identifier)` is true; interfaces fail this check and arbitrary strings require an explicit existing class.

`ServiceBuilder::getService(string)` checks the registry, then a configured definition, and only then attempts `autowireService()`; both configured and autowired construction recurse through `getService()`.
Each identifier is cached separately, so the same identifier returns the same instance and multiple independent instances of one class require multiple identifiers.
Configuration (or pre-registration) is required when raw or builtin values are needed, when an arbitrary identifier, interface identifier, or alternate implementation is needed, or when multiple instances are required.

Autowiring requires `class_exists()` and, for every constructor parameter, a non-builtin `ReflectionNamedType` resolvable via `getService()`:

* Builtin, untyped (`null` type), union, and intersection types throw `AutowireException`; defaults and nullability are not consulted.
* There is no `isInstantiable` check: abstract classes and enums pass `class_exists()` and fail later at `new`.
* Interfaces are never searched for an implementation: an unconfigured interface fails with `InvalidArgumentException`, but can be requested when explicitly configured to a concrete class.

The configured `parameters` array is positional: `array_values()` is applied, keys are ignored, and the result is spread with `...`:

* Positions with a named non-builtin type (class, interface, or enum) must receive a `string` service identifier (a fully qualified class name works), resolved via the full `getService()` order (registry → configured definition → autowire); missing or non-string values cause undefined-key access or `TypeError`, and missing required values cause `ArgumentCountError` at instantiation.
* All other positions (builtin, untyped, union, intersection) pass values through unchanged; union and intersection types therefore throw when autowired but pass through when explicitly configured.

Variadic parameters require explicit configuration for multiple values; autowiring never discovers multiple services:

* Autowired: a builtin variadic (`string ...`) throws `AutowireException`; a named non-builtin variadic resolves at most one service by type name (interface-typed variadics fail unless configured).
* Configured: builtin variadics pass all values through as raw values; named non-builtin variadics resolve the value at the variadic position plus every trailing value as service identifiers.

Service identifiers are arbitrary strings or class names.

== File system access

The `FileSystemAccessService` provides the application-level allowlist and file-operation helpers (`readFile`, `fileExists`, `writeFile`, `deleteFile`, `listFiles`, `isPathAllowed`).
Its configured paths come from `FS_APP_LEVEL_WHITELIST` in `config.php` and are passed to the service in `CoreServiceConfiguration`.
The default app-level paths are `private/init`, `private/sql`, and `private/upload`.

This policy is separate from the `open_basedir` whitelist (`FS_DIRECTORY_WHITELIST` in `config.php`, applied by `RestrictDirectoryAccessStartupAction` via `ini_set`).
After `ApplicationCore::init()`, native calls — including those inside this service — are still enforced by `open_basedir`; this service adds a further allowlist check.
By default it is narrower (`private/*` under `private`), but narrowness is configuration, not enforced in code.

Every configured path must resolve via `realpath()` at construction or construction throws; any existing file or directory is accepted there, but only `readFile`, `deleteFile`, and `isPathAllowed` work with exact file entries — `fileExists` and `writeFile` also require the resolved parent directory to be allowed.
Keep the app-level entries inside `open_basedir`; the service never compares the two lists.

`realpath()` canonicalizes allowed entries, existing targets and parents, and each `listFiles` entry (broken, disallowed, or non-file entries are silently skipped), handling ordinary `..` traversal and symlink resolution; prefix matching requires `DIRECTORY_SEPARATOR`.
`writeFile()` checks `realpath(dirname)`, rejects `is_link(path)`, checks `realpath(path)` when it exists, then writes to `resolvedDir/basename(path)`.

== Routing

Routes are defined as `Route` objects in the `$routes` array constructed by `RoutingConfiguration`.
Each route has a path, an `HttpMethod` enum, a controller service identifier, and an optional handler.
The array keys are not used for matching.

[source,php]
----
// Illustrative example; no current production route uses placeholders.
new Route(
    path: '/some/path/with/{parameter}',
    method: HttpMethod::POST,
    controller: SomeController::class,
    // If omitted, the handler defaults to postAction.
),
----

The controller value is passed to `ServiceBuilder::getService()`.
Lookup order is `ServiceRegistry`, then `CoreServiceConfiguration`, then autowiring; the result is cached.
Autowiring requires an existing class whose constructor parameters are all resolvable class types.
A non-class identifier that is in neither store fails in `autowireService()`.

Both the URL path and the route pattern are trimmed with `rtrim(..., ' /')` (any trailing `/` and space combination) and split with `explode('/')`; segment counts must match.
A route segment starting with `{` matches any one URL segment (including an empty middle segment); an empty pattern segment also matches anything.
Otherwise, non-empty literal segments must match with `===` (case-sensitive).
The host, protocol, port, and query string are ignored.
Extraction uses `trim('/')` and `trim('{}')` with no regular-expression constraints or type conversion; values remain strings.
The first route in `getRoutes()` order wins.
A null or empty path never matches.

The placeholder name is passed as a named handler argument, so the controller method must have a parameter with the same name.
Handler parameter order is irrelevant.

A handler must be a public method with a parameter named `$request`.
`Request` is matched by exact `=== Request::class` (subclasses of `Request` are not accepted); `ValidatedRequest` subtypes may be direct or indirect but must be `readonly` concrete classes (not abstract `ValidatedRequest` itself).
`RequestMapper` finds the candidate by type, but the request-mapping action stores it under the handler argument named `request`, and the facade invokes the handler with those named arguments, so the parameter must be named `$request`.
Only one request parameter is supported.
The handler must return a `Response` or a subclass.

If the handler is omitted, its name is the lowercase HTTP method followed by `Action`: `getAction`, `postAction`, `putAction`, `deleteAction`, or `optionsAction`.

[source,php]
----
class SomeController
{
    public function postAction(Request $request, string $parameter): Response
    {
        // ...
    }
}
----

A path with no matching route returns `new Response(NOT_FOUND)` with `null` content.
Most `Throwable` values from `PreControllerActionFacade::process()` become an empty `500 INTERNAL_SERVER_ERROR` response; `BadRequestException` (request-mapping `TypeError`, validation failure) becomes an empty `400 BAD_REQUEST` response.
Controller-resolution and path-parameter count failures thrown before the `try` block propagate uncaught.

=== Request construction

`RequestFactory::buildRequestFromGlobals()` maps `$_SERVER['HTTPS']`, `$_SERVER['HTTP_HOST']`, `$_SERVER['REQUEST_URI']`, and `$_SERVER['REQUEST_METHOD']` plus `getallheaders()`, `$_POST`, `$_GET`, and `$_FILES` into a `Request`.
`UrlFactory` parses the URL with `parse_url()` and validates the resulting `Url`: protocol must be `http` or `https`, host must pass `ValidateHost`, a present port must be within `1..65535`, while path and query are unvalidated.
`InvalidArgumentException` (unparseable or invalid URL) and `ValueError` (unknown `HttpMethod::from()` value) during `buildRequestFromGlobals()` happen in `runCgi()` before the `handleRequest()` try block, so they are uncaught — `ExceptionResponseService` never converts them into `Response` objects.

=== Adding a page

To add a user-facing page:

. Add a case to `RouteEnum` (`src/Data/Constant/RouteEnum.php`): route paths in `RoutingConfiguration`, `RedirectResponse` targets, and the navigation links in `HtmlPageDataProvider::getNavigationRoutes()` all derive from it, so paths are never hardcoded.
. Register a `Route` for the new path in `RoutingConfiguration`, pointing at the controller service identifier.
. Add the controller with a `getAction(Request $request): Response` handler that sets `ContextKey::PAGE_TITLE`, wraps its content config with `HtmlPageConfigFactory::wrap()`, and returns `TemplateService::generateResponse(...)` (see the Templates section for the full pattern).
. Add the page to the hardcoded `getNavigationRoutes()` map in `HtmlPageDataProvider` when it should appear in the navigation; nested arrays render as submenus.
. Gate the handler with `#[Authenticated(...)]` when it requires a logged-in user, and use a `ValidatedRequest` DTO for `POST` input.

== Error handling and responses

`ApplicationCore::handleRequest()` catches `Throwable` around the pre-controller chain and the controller.
`BadRequestException` becomes an empty `400` response and any other exception becomes an empty `500` response via `ExceptionResponseService`.
No route match, or a falsy controller result, becomes an empty `404` response via `generateDefaultResponse()`.
Validation messages exist only in the exception text, never in the response body; there is no logger.

`Response(status, content, headers)` defaults to `OK`, `null`, and `[]`.
`RedirectResponse(?RouteEnum)` is always `303 SEE_OTHER` with a `Location` header (defaulting to `/`).
`simulateRequest()` preserves headers so tests can assert `Location`, but `ApplicationCore::output()` in `runCgi()` only calls `http_response_code()` and `echo`, never `header()` — redirects and content types currently do not reach browsers.
No `Content-Type` is set anywhere.

== PreControllerAction Chain

Before a controller handler is invoked, `PreControllerActionFacade` runs an ordered chain of `PreControllerAction` implementations.
Each action receives the handler-argument array by reference.
Mutations remain available to later actions and are used for the controller call.
The facade itself receives the initial array by value.

Returning `null` continues the chain.
Any non-null `Response`, including a successful response, stops the remaining actions and the controller, and becomes the request response.

=== Configuration

Register actions in `CoreServiceConfiguration` as positional parameters to `PreControllerActionFacade`:

[source,php]
----
new Service(
    identifier: PreControllerActionFacade::class,
    parameters: [
        AuthorizationPreControllerAction::class,
        RequestMappingPreControllerAction::class,
        ValidationPreControllerAction::class,
    ],
),
----

Actions are not auto-discovered.
A `PreControllerActionFacade` constructed with zero actions invokes the controller directly (the `foreach` is a no-op), but `CoreServiceConfiguration` must still list at least one action identifier; an empty or missing entry does not produce an empty chain via `ServiceBuilder` — it throws.
In the default configuration, authorization runs first, followed by request mapping and validation.
Both `RequestMappingPreControllerAction` (mapping `TypeError` → `BadRequestException`) and `ValidationPreControllerAction` abort via `BadRequestException`, caught in `ApplicationCore` and mapped to a bare `400` response with a `null` body; validation messages survive only in the exception message, not in the response.

=== Authentication

To require authentication for a controller handler, add `#[Authenticated(AccessLevel::NOVICE)]` to the actual route-resolved handler method.
The `AccessLevel` argument is required.
The attribute targets methods, not classes.

The `AuthorizationPreControllerAction` checks the attribute at runtime:

* If the attribute is absent, the endpoint is not blocked by this action.
* If present and no session user exists, a `401 UNAUTHORIZED` response is returned.
* If the session user's access level is below the required level, a `403 FORBIDDEN` response is returned.
* If the level is sufficient, authorization passes and request mapping and validation still run.

`AccessLevel` is an ordered int-backed enum ranging from `NOVICE` to `ADMIN`; comparison is on the integer `value` with `<`, so an equal level passes.
All current gates require the lowest level, `NOVICE`; higher levels exist only as ordered values — no route requires them and no UI changes them, so promote users by updating `user.access_level` manually.
Newly registered users are active `NOVICE` users.
Authorization reads the user data stored in the session and does not reload the user from the database.
The current authentication flow does not enforce the database's `disabled` or `banned` states.

[source,php]
----
#[Authenticated(AccessLevel::NOVICE)]
public function postAction(UserSettingsUpdateRequest $request): Response
{
    // ...
}
----

These responses do not redirect to `/login` or add a `WWW-Authenticate` header.

=== Login and logout

`POST /login` uses the `LoginRequest` validated request, so request mapping and validation run before the controller: missing or too-short fields yield a bare `400` response via `ValidationPreControllerAction`.
Once validation passes, the controller looks up the user by login name and verifies the password.
An unknown login name and a wrong password both return a bare `401 UNAUTHORIZED` response without disclosing which check failed.
On success, the controller calls `startSession()` (which throws `InvalidStateException` when a session is already active, so re-login without logout fails with `500`), stores the session user data, and returns `303 SEE_OTHER` to `/`.
A successful login does not update `lastLoginDate`, and the session ID is never regenerated.

`AuthenticationService` delegates password checking to `PasswordService::verifyAndRehashIfNeeded()`, which verifies with `password_verify()` and, when the stored hash no longer matches the current `PASSWORD_DEFAULT` algorithm, rehashes the password and persists the new hash.

`POST /logout` has no authentication check: it always clears `$_SESSION` (even without an active session) and returns `303` to `/`.
`GET /login` and `GET /register` always return `200`; when already logged in they render the page without the login or registration form.

=== Registration

`POST /register` validates a `RegisterRequest`, returns a bare `400` on password mismatch and a bare `409 CONFLICT` on a duplicate `loginName` (which reveals that the name exists), and otherwise creates an active `NOVICE` user (`registerDate` set to now, `lastLoginDate` set to `null`) and returns `303` to `/login` without logging the user in (no `$_SESSION['user']` is set).
The validated `email` field is discarded — no column or entity property stores it.

=== User settings

`POST /settings` requires `NOVICE` or higher (`401` when anonymous; authorization runs before validation), validates `displayName` (`1..69` characters, not null), updates the user row and `$_SESSION['user']`, and returns `303` to `/settings`.
`GET /settings` has no authentication requirement: anonymous users get the page without the form, logged-in users get the form prefilled with their current display name.

=== Password and field policy

|===
| Field | Constraints

| `email` | `1..255` characters, valid email
| `loginName` | `1..255` characters
| `displayName` | `1..69` characters
| `password` | `10..72` characters and at most `72` bytes
| `passwordRepeat` | `10..72` characters (no byte check)
|===

All listed fields additionally reject `null`.
Password values are marked `#[SensitiveParameter]` on the `UserEntity`, `LoginRequest`, and `RegisterRequest` constructor parameters and on the password-handling methods of `PasswordService` and `AuthenticationService`.
Passwords are hashed with `password_hash(PASSWORD_DEFAULT)`; verification transparently rehashes and persists when `password_needs_rehash()` reports a stale hash.
The `user.password` column is `VARCHAR(128)`.
Short or null login passwords yield `400` (validation) rather than `401`.
The form components mirror these limits with `minlength` and `maxlength` attributes.

=== Request Mapping

Every controller handler must declare a `$request` parameter typed as `Request` or as a concrete subclass of `ValidatedRequest`.
The mapper detects the candidate by type, but the request-mapping action stores the result under the handler argument named `request`, so the parameter must be named `$request` (a `ValidatedRequest $foo` parameter would map and then fail binding with an unknown named parameter).
A missing or non-matching request parameter fails with `500`, not `400` (`RuntimeException` when no request parameter is found; a builtin- or union-typed parameter fails earlier, during type detection).

`Request` receives the original request object unchanged (same instance).
It contains the URL, HTTP method, headers (`getallheaders()`), GET and POST parameters (`$_GET`/`$_POST` or `null` when empty), and optional uploaded files (`$_FILES` or `null`).

A `ValidatedRequest` subclass is constructed before the controller runs.
Its effective constructor must accept the parameter named `rawRequest` typed as `Request $rawRequest`; the inherited constructor from `ValidatedRequest` is sufficient, and a differently named `Request` parameter fails with `Error` (mapped to `500`).
For every other constructor parameter, the mapper looks up a value using the parameter name:

[source,php]
----
$request->postParams[$name] ?? $request->getParams[$name] ?? null
----

A non-null POST value takes precedence over GET; a null POST value falls through to GET.
* Only matching constructor parameter names are mapped; unrelated GET and POST keys are ignored.
* Missing values are passed explicitly as `null`, even when the constructor parameter has a default value, so non-null defaults never apply.
* No scalar type conversion: values pass unchanged, so with `strict_types`, `"123"` does not satisfy an `int` parameter.
* Only `TypeError` during construction becomes `BadRequestException`; other failures become `500`: `Error` for unknown `files` or `rawRequest` parameters, `RuntimeException` for a missing parameter or a non-readonly class.

If uploaded files are present, the complete files array is also passed as `$files`; declare `?array $files = null` when optional or `array $files` when required.
A request carrying `$_FILES` without such a parameter fails with an unknown named parameter (`Error` → `500`); a DTO requiring `array $files` without files in the request fails with `TypeError` (→ `400`).
Mapped request classes must be declared `readonly`; otherwise a `RuntimeException` (→ `500`) is thrown.

In the default pre-controller chain, authorization runs first, followed by request mapping and then validation.
`ValidationPreControllerAction` skips plain `Request` objects and invokes `Validator` for `ValidatedRequest` objects; it depends on mapping having populated `handlerArguments['request']`.
Property attributes implementing `ValidationAttribute` are evaluated (including recursive `ValidateObject` handling); failed validation raises `BadRequestException` whose message is discarded by the bare `400` response.

== Session handling

Sessions are stored in the `session` table (`private/init/init_sqlite.sql`, `private/init/init.sql`, `#[Entity('session')]` in `src/Data/Persistence/SessionEntity.php`).
`RegisterSessionHandlerStartupAction` calls `session_set_save_handler($handler)` during `ApplicationCore::init()` (second of the three default startup actions, before `ResumeSessionStartupAction`).
`SessionHandler` implements `SessionHandlerInterface` and `SessionUpdateTimestampHandlerInterface`, uses `SessionEntityService::findOneBySessionId` and `saveOrUpdate` for `read` and `write` (`read` returns `''` when no row exists), `deleteBySessionId` for `destroy`, `deleteOlderThan(max_lifetime)` (`DELETE WHERE created < now - max_lifetime`) for `gc`, and `sessionIdExists` for `validateId`.
`write()` validates via `Validator` and throws `RuntimeException` on failure; `updateTimestamp()` currently does nothing and returns `true`.
`open()` and `close()` return `true` with only `TODO` locking comments; no locking is implemented.
Garbage collection uses `created` (the insert time, never refreshed on `write`), so a long-lived session can be collected `max_lifetime` after creation even when active; `gc_maxlifetime` itself is not set in `SESSION_OPTIONS`.

`SessionEntity::$data` has `#[ValidateStringSizeBytes(max: 2 ** 24 - 1)]` (the `MEDIUMTEXT` maximum) and `::$sessionId` has `max: 64`; both also carry `#[ValidateNotNull]`.
Enforcement happens in `SessionHandler::write()`; the SQLite `TEXT` column alone does not enforce the limit.

`SessionService::SESSION_OPTIONS` passed to `session_start()`: `name = 'session'`, `cookie_lifetime = 3600`, `cookie_secure = false` (`// TODO: Change for live`), `cookie_httponly = true`, `cookie_samesite = 'Strict'`, `use_strict_mode = true`, `use_only_cookies = true`.
`resumeSession()` (called by `ResumeSessionStartupAction`) throws `InvalidStateException` when a session is active, returns without starting when `$_COOKIE['session']` is unset, and otherwise calls `session_start()`.
`startSession()` throws when a session is active and otherwise calls `session_start()` unconditionally.
`destroySession()` always clears `$_SESSION`, then returns early when inactive; when active and `session.use_cookies` is set, it clears the `session` cookie via `setcookie('session', '', 0, path, domain, secure, httponly)` (no `samesite`, expiry `0` rather than a past timestamp) and then calls `session_destroy()`.

On login success, the controller stores `SessionUserData(id, displayName, accessLevel)` as `$_SESSION['user']`; `AuthorizationPreControllerAction` (as well as `UserSettingController`, `LoginController`, and `RegisterController::getAction`) reads it via `SessionService::getUserData()`.

== Templates

`TemplateService` can render any `TemplateConfig` directly.
Use `HtmlPageConfigFactory::wrap()` when the standard `HtmlTemplate` page shell is desired.
Before calling `wrap()`, set `ContextKey::PAGE_TITLE` to a `string` via `ContextService::setContext()`.
`wrap()` synchronously calls `HtmlPageDataProvider::getPageTitle(): string`, which returns `getContext(PAGE_TITLE)`; an unset or `null` title causes a `TypeError`.
The page title is copied into the wrapped config at `wrap()` time; later context changes do not affect it.
`ContextService` type-checks context values: each `ContextKey` backed value is the expected `gettype()` result (currently only `PAGE_TITLE = 'string'`).
`setContext()` stores `null` as-is; for non-null values with a differing type it throws `InvalidArgumentException`.

[source,php]
----
use SmolCms\Config\Templates\HtmlPageConfigFactory;
use SmolCms\Config\Templates\SimpleContentComponentConfig;
use SmolCms\Data\Constant\ContextKey;
use SmolCms\Data\Request\Request;
use SmolCms\Data\Response\Response;
use SmolCms\Service\Core\ContextService;
use SmolCms\Service\Core\TemplateService;

readonly class ExampleController
{
    public function __construct(
        private TemplateService $templateService,
        private HtmlPageConfigFactory $htmlPageConfigFactory,
        private ContextService $contextService,
    ) {
    }

    public function getAction(Request $request): Response
    {
        $this->contextService->setContext(ContextKey::PAGE_TITLE, 'Example page');

        return $this->templateService->generateResponse(
            $this->htmlPageConfigFactory->wrap(
                new SimpleContentComponentConfig(content: 'Page content here'),
            ),
        );
    }
}
----

`HtmlPageConfigFactory::wrap()` delegates to `HtmlPageDataProvider`: the page title comes from `ContextService`, the language is hardcoded as `getLanguage() = 'en'`, and the navigation is a hardcoded `getNavigationRoutes()` map of `RouteEnum` values.
The content `TemplateConfig` must return a single-root `[ContentClass => params]` tree that can be built into a `Template` for `HtmlTemplate::$contentSlot` (only the first entry is kept); it only needs to carry page-specific data and parameters.

A content config is a (readonly) class implementing `TemplateConfig`.
Simplified illustration (`SimpleContentPageConfig` exists only here; the codebase ships `SimpleContentComponentConfig(content, extraComponents = [])` with the same structure plus spread `extraComponents` for nested forms):

[source,php]
----
use SmolCms\Config\Templates\TemplateConfig;
use SmolCms\Template\Component\SimpleContentComponent;

readonly class SimpleContentPageConfig implements TemplateConfig
{
    public function __construct(private string $content)
    {
    }

    public function getConfig(): array
    {
        return [SimpleContentComponent::class => [$this->content]];
    }
}
----

A typed config class provides typing for its own constructor properties, but `getConfig()` returns a positional, runtime-processed tree that is spread into the constructor.
Only string keys with `class_exists($key) === true` recurse as nested `Template` values; their value must be an `array` or a `TemplateException` is thrown.
Other entries are passed as-is in order.
The top level uses `array_key_first()` as the root template class.

Every template and component must implement `Template` and provide `render(): string` (enforced via the `buildTemplateFromConfig(): Template` return type plus the `render()` call; a non-`Template` class causes a `TypeError`, not a `TemplateException`):

[source,php]
----
use SmolCms\Template\Template;

readonly class ExampleComponent implements Template
{
    public function render(): string
    {
        return '<p>Example content</p>';
    }
}
----

Template rendering does not escape values automatically, and the current `Head`, `SimpleContent`, `UserSettings`, and navigation components interpolate values raw, including user-controlled display names.

Successful template responses use HTTP 200 and contain the rendered string.

[#_validation]
== Validation

`Validator::validate(object $objectToValidate): ValidationResult` reflects over all properties (including private ones) and instantiates attributes that are `instanceof ValidationAttribute`.
`PropertyValidationAttribute::validate(mixed $value): bool` rules return the pass or fail result and `ValidateObject` recurses into nested objects; other direct `ValidationAttribute` implementations are silently ignored.
Different attribute classes may stack on one property; the same class cannot repeat because none of the built-in attributes is `IS_REPEATABLE`.
Messages are keyed by property name and the last failing attribute overwrites: a `string` (`'Failed validation: <Class> - <getErrorMessage()>'`) for property rules, or an `array` of nested messages for `ValidateObject`.

`ValidateObject()` skips `null`, otherwise requires an `object` and validates it recursively; a non-object, non-null value causes a `TypeError` (the `validate()` parameter is typed `object`), and its `getErrorMessage()` is never used by the `Validator`.

The built-in validation attributes (all `TARGET_PROPERTY`) are:

* `ValidateRange(float $min, float $max)`: `null` passes, non-`int`/`float` values (including numeric strings) fail, otherwise inclusive bounds
* `ValidateAllowList(array $allowValues = [])` using strict `in_array` comparison; `null` passes
* `ValidateDenyList(array $denyValues = [])` using strict `!in_array` comparison; `null` passes unless `null` is denied
* `ValidateEmail()` using `FILTER_VALIDATE_EMAIL`; `null` passes
* `ValidateHost(int $type = ALLOW_ALL)` with the `IPV4 = 1`, `IPV6 = 2`, `DOMAIN = 4` bitmask via `FILTER_VALIDATE_IP`/`FILTER_VALIDATE_DOMAIN`; `null` passes
* `ValidateNotNull()` rejecting only `null` (`!== null`)
* `ValidateStringSize(int $minLength = 0, ?int $maxLength = null)`: `null` passes, non-strings fail, `mb_strlen` bounds are inclusive, a `null` max means no upper limit
* `ValidateStringSizeBytes(int $max)`: `null` passes, `strlen($value) <= $max`, max-only, with no `is_string` guard (non-strings may throw `TypeError`)
* `ValidateObject()` for recursive nested-object validation

Except for `ValidateNotNull` (and `ValidateDenyList([null])`), all validators pass `null`.

Usage:

[source,php]
----
use SmolCms\Service\Validation\Attribute\ValidateAllowList;
use SmolCms\Service\Validation\Attribute\ValidateDenyList;
use SmolCms\Service\Validation\Attribute\ValidateRange;
use SmolCms\Service\Validation\Validator;

class Foo
{
    public function __construct(
        #[ValidateRange(min: 10, max: 100)]
        private float $floatVal,
        #[ValidateRange(min: -10, max: 0)]
        private int $intVal,
        #[ValidateAllowList(['ALLOWED', 1, true])]
        private mixed $mixedAllow,
        #[ValidateDenyList(['DENIED', 'ALSO_DENIED'])]
        private string $stringDeny,
    ) {
    }
}

$validator = new Validator();
$foo = new Foo(
    floatVal: 15.0,
    intVal: -1,
    mixedAllow: 'ALLOWED',
    stringDeny: 'Not denied',
);
$result = $validator->validate($foo);
var_dump($result->isValid());     // bool(true)
var_dump($result->getMessages()); // array(0) { }
----

To add a validation attribute, declare a PHP attribute targeting properties and implement `PropertyValidationAttribute` (both `validate(mixed $value): bool` and the `getErrorMessage(): string` method inherited from `ValidationAttribute`); no validator registration is required.
A bare `ValidationAttribute` without `Validator` support is ignored; add `IS_REPEATABLE` when the same rule type must repeat on one property.

== Database and persistence

The default runtime database is SQLite at `private/db/smolcms.sq3`.
The active SQLite schema in `private/init/init_sqlite.sql` contains `user`, `session`, `article`, and `migration` tables.
`private/init/init.sql` is the MySQL schema (used by `--reset-db` when the PDO driver is `mysql`); using MySQL requires changing the `PDO` service DSN in `CoreServiceConfiguration` and installing `pdo_mysql`.

Persisted entities use `#[Entity(table: ...)]` and `#[Id]`.
Database snake_case columns map to camelCase entity properties in both directions via `CaseConverter`, and hydration calls `new $entityClass(...$entityProps)`, so every entity property must be an accepted (named) constructor parameter; unknown columns are dropped and missing values become `null`.
Saving via `EntityService` currently requires `get<Prop>()` for every entity property and `set<IdProp>()` for the `#[Id]` property to backfill `lastInsertId`.

Beyond the case conversion, `EntityService` maps `DateTime` properties and backed enum properties automatically in both directions: database values hydrate into `DateTime` objects or enum instances, and entities serialize `DateTime` as `Y-m-d H:i:s` strings and enums as their backing values for storage.
Only `DateTime` is supported (not `DateTimeImmutable` or `DateTimeInterface`); null or missing values stay `null`, and an invalid enum value throws from `::from()`.

To persist a new kind of entity: create its table through a migration (`--generate-migration`, then `--migrations`), add an entity class with `#[Entity(table: ...)]` and `#[Id]`, and add a thin `EntityService` subclass for it (autowired like `UserService`).
The unused `article` entity and `ArticleService` are an in-repo example.

Queries are built with `QueryCriteria` and `QueryBuilder`.
`select()`, `update()`, and `delete()` start a criteria and fix its query type; conditions are collected with `andWhere()` and `orWhere()`, where the first condition must be an `andWhere()`; `withParameters()` supplies (and overwrites) bound values; `maxResults()` and `skipResults()` translate into a `LIMIT` clause emitted as `LIMIT [offset,] count` with `PHP_INT_MAX` substituted when only an offset is set.
`WHERE` is emitted as `WHERE 1 AND/OR ...`.
Select criteria enumerate all entity fields, update criteria set all entity fields (including the id column), and criteria cannot express inserts; `EntityService` builds insert statements from the entity's field values instead.

The `article` table, entity, and service exist (`slug`, `title`, `state`, `content`, `created`, `updated`) but are currently unreferenced — no routes or controllers implement article listing or editing.
`UserEntity::$lastLoginDate` is always `NULL` because login never writes it; `state` is hardcoded to `active` on registration.

== Image uploads

Users with `NOVICE` or higher (`401` when anonymous, `403` when below the level) can submit a multipart `POST /upload-image` with the field `image`; `GET /upload-image` renders the form.
`ImageUploadController::postAction` manually runs `ImageUploadValidator` (it is not a `ValidatedRequest`): the validator requires `files['image']` to be an array with `tmp_name` and `name` and requires `is_uploaded_file()`, ignoring the `error`, `size`, and MIME fields entirely; failure returns `400`.

On success the controller runs `file_get_contents(tmp_name)` (`false` returns `500`; the upload temporary directory must be in `FS_DIRECTORY_WHITELIST`), then gates on `ImageTypeDetectionFacade` (`Png`, `Jpeg`, `Avif` detectors, first match wins; `null` returns `400`).
PNG checks the first 4 bytes for `89504E47`, JPEG checks `FFD8FF`, and AVIF checks `ftypavif` or `ftypavis` at offset 4.
The detected type is otherwise discarded.

Accepted uploads call `ImageProcessorFacade` (`Png`, `Jpeg`, `Avif`, in that order) with `basename()` of the client-supplied name; each processor runs generic `imagecreatefromstring()` and then `ImageStorageService::storeImage()` with its fixed type into `IMAGE_STORAGE_DIR` (`private/upload/img`) under that basename.
That is three sequential overwrites of one path (`imagepng` quality 9, `imagejpeg` quality 100, `imageavif` quality 100): the final bytes are AVIF while the original basename and extension are preserved.
A same-name re-upload overwrites silently; a missing or disallowed directory, or an `imagecreatefromstring()` failure, throws and becomes `500`.
Success returns `303` to `/`.
There is no public image-delivery route, upload quota, deduplication, or extension normalization; `private/` is not web-exposed.

`ext-gd` with PNG, JPEG, and AVIF support is required — AVIF support is required for every successful upload under the current configuration, not only "where used".
Image handling should be treated as experimental.
Functional tests must stub `ImageUploadValidator` because `is_uploaded_file()` fails outside real uploads.

== Testing

Install dependencies and run the full suite from the repository root:

[source,shell]
----
composer install
vendor/bin/phpunit
----

Test classes live in the `SmolCms\Test\` namespace (mapped to `tests/` via `composer.json` `autoload-dev`); the shared test utilities live in `SmolCms\TestUtils\` (mapped to `tests/TestUtils/`).

`SimpleTestCase::setUp()` populates properties tagged with `#[Mock(...)]` using PHPUnit mocks and properties tagged with `#[Stub(...)]` using PHPUnit stubs.
These attributes only populate test-object properties; they do not replace services in the application container.

[source,php]
----
use PHPUnit\Framework\MockObject\MockObject;
use SmolCms\Config\CoreServiceConfiguration;
use SmolCms\Data\Business\ServiceRegistry;
use SmolCms\Service\Core\ServiceBuilder;
use SmolCms\TestUtils\SimpleTestCase;
use SmolCms\TestUtils\Attributes\Mock;
use SmolCms\TestUtils\Attributes\Stub;

class ServiceBuilderUnitTest extends SimpleTestCase
{
    private ServiceBuilder $serviceBuilder;

    #[Mock(CoreServiceConfiguration::class)]
    private CoreServiceConfiguration|MockObject $serviceConfiguration;

    #[Stub(ServiceRegistry::class)]
    private ServiceRegistry|MockObject $serviceRegistry;

    protected function setUp(): void
    {
        parent::setUp();
        $this->serviceBuilder = new ServiceBuilder($this->serviceConfiguration, $this->serviceRegistry);
    }
}
----

The `|MockObject` union is the convention used throughout the suite, and `parent::setUp()` is required to populate the doubles.

`FunctionalTestCase` builds a functional application environment with `sqlite::memory:`, loads `private/init/init_sqlite.sql`, replaces `ContextService` with `TestContextService`, and permits `open_basedir=/` by overriding the `RestrictDirectoryAccessStartupAction` parameters to `['/']` before `ApplicationCore::init()`.
Use its protected `simulateRequest(Request): Response` method to test requests without a web server.
The in-memory database is shared by test methods within a functional test class; setup clears sessions but does not isolate database rows per method.
`FileSystemAccessService` still enforces `FS_APP_LEVEL_WHITELIST` in functional tests; keep test files under `private/init`, `private/sql`, or `private/upload`.

`#[Autowire]` requires a typed property with one named class type (untyped, union, or intersection properties fail); it resolves that type through the functional test service container.
Subclasses of `SimpleTestCase` or `FunctionalTestCase` overriding `setUp()` must call `parent::setUp()` — otherwise `Mock`/`Stub`/`Autowire` population and (functional) session clearing are skipped.

`loginUser($loginName, $displayName)` creates a `NOVICE` user with password `secure-password-123` when missing and logs in via `POST /login`; call it per test because sessions are cleared while database rows persist across methods in a class.

To override a service for a test class, call `self::registerTestServices()` in `setUpBeforeClass()` after `parent::setUpBeforeClass()`.
This replaces service definitions and rebuilds the service builder, registry, application core, and in-memory database (`MyExternalClient` below is a placeholder for a real existing class; `parameters` are positional — see <<_configuring_services>>):

[source,php]
----
public static function setUpBeforeClass(): void
{
    parent::setUpBeforeClass();
    self::registerTestServices(
        new Service(
            identifier: MyExternalClient::class,
            parameters: ['http://localhost:9999'],
        ),
    );
}
----

`phpunit.xml` runs the `tests/` directory with `beStrictAboutOutputDuringTests`, `failOnAllIssues`, `displayDetailsOnAllIssues`, and `beStrictAboutCoverageMetadata`; output, deprecations, warnings, notices, risky tests, and other PHPUnit issues fail the run and must be fixed.
Execution order is `depends,defects`.

[#_cli_commands]
== CLI Commands

The application supports CLI commands through `php src/app.php`.
Flags use a `--` prefix.
Non-flag tokens following a recognized flag are collected as that flag's `$arguments` array in `$argv` order and passed to `execute()`; separate arguments with spaces and quote values containing spaces.
Currently only `--generate-migration` uses `arguments[0]`; `--migrations` and `--reset-db` ignore arguments.
Recognized command executors are registered positionally as parameters to `CliCommandHandler` in `CoreServiceConfiguration`.
A single invocation may contain several distinct flags; each executor whose flag is present runs at most once, in the order its flag first appears on the command line.
Repeating a flag does not re-run it; the last occurrence's arguments win.
`--noconfirm` never runs as an executor.

`runCli()` exits `0` whenever `PHP_SAPI` is `cli` (even when only printing the command list for unknown flags), so `runCgi()` only runs under a non-CLI SAPI.
Functional tests use `TestContextService` and force non-CLI mode for `simulateRequest()`.

To add a command, add a case to the `CliCommandFlag` enum, create a class implementing `CliCommandExecutor`, and add the executor to the `CliCommandHandler` service definition.
The enum `value` is the literal flag text without `--`.
The executor's `handles()` must return the new case and `helptext()` supplies the command-list output.
When the executor has builtin or string constructor dependencies, add its own `Service` definition, as done for `MigrationsExecutor`.
`--noconfirm` is a global modifier consumed by the handler; it is not an executor.

=== Available commands

|===
| Flag | Description

| `--generate-migration "<description>"`
a|Creates a timestamped migration skeleton in `private/sql`, named `YYYY-MM-DD_HH-MM-SS__<sanitized-description>.sql`, where `<sanitized-description>` replaces every `[^a-zA-Z0-9_-]` character with `_`, trims leading and trailing `_`, and falls back to `migration`.
The file content is `-- Migration: <original description>\n`.
Only the first argument is used; extra tokens are ignored.
An empty or missing description prints the usage text and creates nothing.
Generation does not execute the migration.

| `--migrations`
a|Scans `private/sql` non-recursively via `FileSystemAccessService::listFiles` for regular allowed files ending case-sensitively in `.sql`, sorts them by filename, and executes files not recorded in the `migration` table.
Comparison and recording use the `basename()` against `migration.filename`.
Successful migrations are recorded; already-recorded files are skipped, and empty files (including whitespace-only files) are skipped without being recorded but still count as pending for the confirmation prompt.
Confirmation lists the pending basenames and is required only when pending files exist, unless `--noconfirm` is supplied; only `y` (case-insensitive) proceeds — any other answer, including `yes`, aborts.
A failed migration is not recorded, later files are not attempted, and `Migrations complete.` is not printed.
Arguments to `--migrations` are ignored, and a missing directory prints an error.

| `--reset-db`
a|Destructively drops tables and reloads the driver-specific schema: SQLite drops all tables except `sqlite_%`, while MySQL drops all tables in `DATABASE()`.
The default SQLite configuration reloads `private/init/init_sqlite.sql`.
The MySQL branch sets `FOREIGN_KEY_CHECKS = 0` before the drops and re-enables it to `1` after the drops and before reloading `private/init/init.sql`.
Confirmation is required unless `--noconfirm` is supplied.
Unlike `--migrations`, the prompt is unconditional even with no tables; with no tables it prints `No tables to drop.` and still reloads the schema.

| `--noconfirm`
a|Modifier for `--migrations` and `--reset-db`; suppresses their confirmation prompts.
It does not execute by itself and has no effect on `--generate-migration`.
|===

=== Usage examples

Generate a migration file:

`php src/app.php --generate-migration "add users table"`

Edit the generated SQL file, then run pending migrations with confirmation:

`php src/app.php --migrations`

Run pending migrations without confirmation:

`php src/app.php --migrations --noconfirm`

Reset the database with confirmation:

`php src/app.php --reset-db`

Reset the database without confirmation:

`php src/app.php --reset-db --noconfirm`

`--noconfirm` may appear before or after the command; its position does not affect suppression, but non-flag tokens immediately after `--noconfirm` are consumed as its ignored arguments.
If no executable command flag is provided, such as with no arguments, an unknown flag, or only `--noconfirm`, the handler prints the available-command list.
Unknown `--` flags are ignored and reset the current flag, so following bare tokens are also ignored until the next recognized flag.
Bare tokens before any recognized flag (or after an unknown flag) are ignored; bare tokens after a recognized flag become that flag's arguments.

== Development rules

Every PHP file must start with `declare(strict_types=1);`.
Do not use `@` to suppress warnings or notices in application code (`src/`), and do not use deprecated functionality.
Tests must have no failures, errors, warnings, notices, risky tests, or skipped tests.
No build, lint, typecheck, or code-generation task is configured; `phpunit.xml` is the verification config.

== Security considerations

The project is a learning project and is not production-hardened; do not deploy it to production as-is.
Known gaps:

* `cookie_secure = false`
* no session locking
* session IDs that are never regenerated
* minimal upload validation with fan-out PNG/JPEG/AVIF processing
* no automatic template escaping (user-controlled display names render raw)
* best-effort `open_basedir` restriction — defense in depth, not a substitute for OS permissions or web-server access controls
* a file-system allowlist that guards against wrong-path writes but not against check-then-use races, symlink swaps, or direct native-call bypasses
* CGI output that drops headers, so redirects do not reach browsers
* no CSRF tokens on `POST /login`, `/register`, `/settings`, `/logout`, or `/upload-image` (`SameSite=Strict` is the only cross-site mitigation)
* no rate limiting
* a `409` on duplicate registration that enables login-name enumeration
* no static-serving deny for `/src/` — do not serve `private/` or `src/` statically
* unenforced `disabled` and `banned` user states

See <<#_directory_access_restrictions,Directory Access Restrictions>>, Session handling, Image uploads, and Templates for details.
