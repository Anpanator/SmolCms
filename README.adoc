== Project constants

Global constants are defined in `constants.php` at the project root.
These constants will always be available (even in testing).
It is not recommended to use them for configuration purposes, such as credentials.

== Early startup configuration

If you need to run bootstrapping code very early in the application startup, you can utilise the `ApplicationStartupHandler` service.

In its service definition, it will take any number of `StartupAction` parameters, which will be run, in order, when the application starts.

[source,php]
----
new Service(
    identifier: ApplicationStartupHandler::class,
    parameters: [
        MyStatupAction::class,
        FancyStartupAction::class,
    ]
)
----

== Configuring services

Check the `ServiceConfiguration` class.
For now, it's just hard-coded in the constructor.
Configuration of a new service is only necessary if:

* You need multiple instances
* You have scalar/array type dependencies

Everything else will be autowired.

If you manually configure a service, and it depends on another service that does *not* have a service configuration, you can set the fully qualified classname of the service instead (e.g. `MyService::class`).
If you have a service definition, you can set the identifier of the service you want to inject.
The `parameters` array needs to have the same order as the constructor parameters.

Variadic parameters in the form of `MyService ...$services` are supported for services with a configuration, but not for autowiring.

The `class` parameter can be omitted if the identifier is the fully qualified class name.

== File system access

The `FileSystemAccessService` provides secure file system operations restricted to a configured set of allowed directories.

Configuration for allowed paths is currently a constant in the service.

All paths are resolved via `realpath()` before any operation, preventing directory traversal attacks.
If a path does not resolve or falls outside the allowed directories, a `FileAccessException` is thrown.

Available methods:

* `readFile(string $path): string` — reads and returns file content
* `fileExists(string $path): bool` — checks whether a file exists
* `deleteFile(string $path): void` — deletes a file
* `listFiles(string $path): array` — returns file names in a directory (skips symlinks pointing outside allowed paths)

== Routing

You can define routes in the `RoutingConfiguration` class, similar to the service configuration.

Controllers are treated like services.
So in the simplest case, you use the fully qualified classname for the controller, e.g. `MyController::class`.
Alternatively, you can use the controllers service identifier.

Routes can contain path parameters in the form of `/some/path/with/\{parameter\}`.
Every path parameter must exist in the handler function with the same name (either untyped, mixed or type string, which is recommended).

A handler *must* also have a `$request` parameter.
The order of all these parameters is irrelevant.
If the handler configuration is omitted, the handler name is assumed to be `HTTP Method + 'Action'`, e.g. `getAction`, `postAction`, etc.

So with the example path above and a POST request, you'd need a handler method like this:

[source,php]
----
class SomeController {
    public function postAction(Request $request, string $parameter): Response
    {
        // ...
    }
}
----

=== Request Mapping

The `$request` parameter in Controller actions can either be of type `Request` or a subtype of `ValidatedRequest`.

Request::
Contains raw parameters and headers of the request.

Subtype of ValidatedRequest::
If a custom subtype of ValidatedRequest is used instead of the plain `Request` class, all `POST` and `GET` parameters will be mapped into the properties of this class with the same name.
When there are both query and post parameters of the same name, the post one will be used.
+
The mapping will be done through the class constructor, so all parameters that should be mapped need to be present as a constructor parameter, including one called `$rawRequest`, which will be filled with the standard `Request` object.
+
Finally, any validation attributes present on the mapped properties will be evaluated.
For details, refer to the <<_validation>> section.

== PreControllerAction Chain

Before a controller handler is invoked, the `PreControllerActionFacade` runs an ordered chain of `PreControllerAction` implementations.
Each action can modify the handler arguments or short-circuit the request by returning a `Response` (e.g. a 401).

=== Configuration

Register actions in `CoreServiceConfiguration` as parameters to
`PreControllerActionFacade`, mirroring the `ApplicationStartupHandler` pattern:

[source,php]
----
new Service(
    identifier: PreControllerActionFacade::class,
    parameters: [
        RequestMappingPreControllerAction::class,
        ValidationPreControllerAction::class,
    ]
)
----

=== Authentication

To require authentication for a controller handler, add the `#[Authenticated]` attribute to the handler method.
It accepts an optional `AccessLevel` parameter.

The `AuthorizationPreControllerAction` (registered in the `PreControllerActionFacade` chain) checks for this attribute on the target method at runtime:

* If the attribute is absent, the endpoint is openly accessible.
* If present and the user is not logged in, a `401 UNAUTHORIZED` response is returned.
* If present and the user's access level is below the required level, a `403 FORBIDDEN` response is returned.
* Otherwise, the request proceeds.

[source,php]
----
#[Authenticated(AccessLevel::NOVICE)]
public function postAction(UserSettingsUpdateRequest $request): Response
{
    // ...
}
----

== Templates

If you want to generate responses from templates, you can do so by using the `TemplateService` together with `HtmlPageConfigFactory` in a controller action.
Before calling `wrap()`, set any context values (such as the page title) via `ContextService`:

[source,php]
----
public function getAction(Request $request): Response
{
    $this->contextService->setContext(ContextKey::PAGE_TITLE, "My Page Title");
    return $this->templateService->generateResponse(
        $this->htmlPageConfigFactory->wrap(
            new ArticleTemplateConfig(articleContent: "Page content here"),
        )
    );
}
----

`HtmlPageConfigFactory::wrap()` assembles the full HTML page by combining the given content config with global context (language, navigation routes, page title) sourced from `HtmlPageDataProvider`.
This means content configs only need to carry page-specific data.

Your content config is a class implementing the `TemplateConfig` interface:

[source,php]
----
readonly class ArticleTemplateConfig implements TemplateConfig
{
    public function __construct(private string $articleContent) {}

    public function getConfig(): array
    {
        return [ArticleComponent::class => [$this->articleContent]];
    }
}
----

This will ensure that autocompletion and proper typing will be available.

Every template and component needs to implement the `Template` interface.

[source,php]
----
readonly class HeadComponent implements Template
{

    public function __construct(
        private string $pageTitle
    )
    {
    }

    public function render(): string
    {
        return <<<HTML
        <head>
            <title>$this->pageTitle</title>
            <link type="text/css" rel="stylesheet" href="/public/css/main.css">
        </head>
        HTML;
    }
}
----

== Validation

For validation on object properties, the generic `Validator` service can be used.
The object to validate is simply passed into its `validate()` method.
For validation to work, you will need to add attributes implementing the `PropertyValidationAttribute` interface on the object properties (multiple are supported).
If you want to have nested object validation, simply add the `ValidateObject` attribute to the property.

Usage:

[source,php]
----
class Foo {
    public function __construct(
    #[ValidateRange(min: 10, max: 100)]
    private float $floatVal,
    #[ValidateRange(min: -10, max: 0)]
    private int $intVal,
    #[ValidateAllowList(['ALLOWED', 1, true])]
    private mixed $mixedAllow,
    #[ValidateDenyList(['DENIED', 'ALSO_DENIED'])]
    private string $stringDeny,
) {
}
}

$foo = new Foo(
    floatVal: 15.0,
    intVal: -1,
    mixedAllow: 'ALLOWED',
    stringDeny: 'Not denied'
);
$result = $validator->validate($foo);
var_dump($result);
----

To support a new validation attribute, you only need to create it and have it implement the `PropertyValidationAttribute` interface.
The validator will then use it automatically.

== Testing

For ease of testing, the `Mock` attribute, `SimpleTestCase` and `FunctionalTestCase` classes have been introduced.

The `setUp()` method will automatically put an unconfigured test double into the property you use the `Mock` attribute on.

Usage:

[source,php]
----
class ServiceBuilderTest extends SimpleTestCase
{
    private ServiceBuilder $serviceBuilder;
    #[Mock(ServiceConfiguration::class)]
    private ServiceConfiguration|MockObject $serviceConfiguration;
    #[Mock(ServiceRegistry::class)]
    private ServiceRegistry|MockObject $serviceRegistry;
//...
}
----

Note: The property type hinting is not necessary and just used for convenient autocompletion.

Additionally, the `FunctionalTestCase` class will provide an `ApplicationCore` that will allow you to simulate requests even without a web server.
This is useful when you want to create automated tests for JSON api endpoints for instance.

To override a service for a specific test class, call `self::registerTestServices()` in `setUpBeforeClass()` after `parent::setUpBeforeClass()`.
This replaces the service in the container and reinitialises the `ApplicationCore`, so all tests in the class will use the new service.
`FunctionalTestCase` itself already uses this mechanism to replace `PDO` with an SQLite in-memory instance.

[source,php]
----
public static function setUpBeforeClass(): void
{
    parent::setUpBeforeClass();
    self::registerTestServices(
        new Service(
            identifier: MyExternalClient::class,
            parameters: ['http://localhost:9999'],
        )
    );
}
----

== CLI Commands

The application supports CLI commands.

Flags are specified with a `--` prefix.
Arguments following a flag are passed to the corresponding executor.
Flag arguments are separated by spaces.
If a single argument requires spaces, the argument needs to be quoted.

All commands are registered as `CliCommandExecutor` parameters in the `CliCommandHandler` service definition.

=== Available commands

|===
| Flag | Description

| `--migrations`
| Reads `.sql` files from `private/sql/`, compares them against an internal `migration` table, and executes any pending migrations in sorted order. Skips already-executed files. Prompts for confirmation unless `--noconfirm` is also specified.

| `--reset-db`
| Drops all user tables in the database (SQLite or MySQL). For MySQL, temporarily disables foreign key checks to avoid constraint errors. Prompts for confirmation unless `--noconfirm` is also specified.

| `--noconfirm`
| Suppresses interactive confirmation prompts. Can be combined with other flags (e.g. `--migrations --noconfirm`).
|===

=== Usage examples

Run pending migrations with confirmation::
`php src/index.php --migrations`

Run pending migrations without confirmation::
`php src/index.php --migrations --noconfirm`

Reset the database::
`php src/index.php --reset-db`

If no recognized flag is provided, the handler prints the list of available flags.
