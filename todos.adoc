== Image Upload / Processing

* User uploads an image
* Image gets processed (rename the "process" method to "sanitize" the purpose here is simply to strip any exif data and make sure the uploaded image is in its proper format)
* Image gets stored in /private/upload/img directory
* Synchronous process ends here
* Storage locations need to be configurable in root config.php

== Post upload process

* General image naming and storage rules:
** file names are the file's sha-265 checksum
** storage locations are further divided by the first 2 characters of the file name (to keep directory sizes low)
** When resizing is needed: Always keep aspect ratio
* There should be a new cli command to initiate image processing.
** Name: --process-images
** Parameter (not flag): batch processing size
* Create thumbnail
** Format: Avif
** Max size: 512x512
** Compression level with GD: 66
** Storage location: /public/img/thumb
* Create image for viewing
** Format: WebP
** Max size: 2048x2048
** Compression with GD: 66
** Storage location: /private/img/sample
* Create image for download:
** Max size: 16384x16384
** Storage location: /private/img/dl
** Image transcoding rules for download:
*** JPEG -> JPEG (no transcode, just copy)
*** PNG -> WebP (lossless mode, best compression mode)
*** AVIF -> AVIF (no transcode, just copy)
*** WebP -> WebP (no transcode, just copy)
* Every image upload needs to be recorded in the database:
** Which user uploaded it
** Time of upload
** Filenames of thumbnail, sample/viewing and download image
* The new command for the post upload processing:
** Should be run every minute, processing up to 100 images
** Should not run if another worker process is already running this command

== Frontend changes

== Image serving specialties:

* Thumbnails may be served directly from /public (already possible)
* Sample and download images, however, must only be available to logged in users (NOVICE or higher)
* These images are in /private/ and as the name suggests, this is not publicly served by nginx, and this must remain that way
* To serve the files anyway, utilize the X-Accel-Redirect header from nginx
** More information might be found here: https://docs.nginx.com/search.html#q=x-accel-redirect and here: https://dev.to/gbhorwood/nginx-serving-private-files-with-x-accel-redirect-57dl
* There must be a dedicated controller for requesting these files, it should simply take the image file name as a query param of a GET request
* Consequently, all affected image tags on the frontend need to request this controller endpoint, instead of a direct file url

* Post processing, images may need to go through a review process
* If the AccessLevel of the uploader is WIZARD or higher, the mod queue is skipped and the image is immediately accepted
* Needs a new frontend view and associated controllers / actions
